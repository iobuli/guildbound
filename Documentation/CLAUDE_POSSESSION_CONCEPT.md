# Claude, the Possession experiment and where it could go

Written by Codex for the boss on 2026-10-12. This is a reasoning handoff, not an instruction to start building. The boss asked for a substantial, conversational account of the application, the work already done, its Rust execution, and a possible path toward a neural controller. All implementation changes remain uncommitted for you to verify. I have reread the current code for this note. I have not launched the viewer, changed the controller, or run builds or tests during this documentation task.

The boss has now clarified the direction: the running game should have no LLM dependency. It should use one compact, deterministic local algorithm to coordinate the whole character, run cheaply and quickly, and repair movement together. That sounds feasible and is a clearer first goal than training a neural policy. The existing LLM-facing Possession tools can remain useful as optional development controls for describing or inspecting a motion; they should not be required by the built game, called per frame, or placed in its control loop. Preauthored clips, fitted rig data, contact intent, and gameplay state are enough inputs for a local controller. A character physically hopping on one leg is also feasible, but that specifically requires physical contacts and bounded joint forces. The current code has pose correction and kinematic foot anchoring, not that controller. A neural network is optional future work, not a prerequisite and no longer the recommended goal.

The algorithm I would investigate is a deterministic whole-body controller, not a pile of independent per-joint patches. Each update would gather one coherent state: root and joint poses and velocities, body proportions, desired motion phase, hand/foot targets, and measured foot contacts. It would form one small constrained solve for the changes to joint angles or accelerations that best meet several tasks at once: follow the reference pose, keep planted feet and hands on reachable targets, preserve limb lengths, keep joints in range, keep arms outside the fitted torso, and produce a plausible body trajectory. Use a clear priority order: first obey joint, reach, collision, and active-contact limits; then preserve balance and the boss's requested task; then track style and pose; finally minimize abrupt changes and unnecessary effort. A single coordinated correction means a lower-priority pose preference gives way when it conflicts with a hard contact or reach constraint. It does not mean one magic formula can repair arbitrary bad assets without meaningful data.

There are two useful levels of this same approach. A fast kinematic whole-body IK/optimization pass can coordinate a skeleton and make clips look consistent, but it cannot make the body genuinely balance or hop; it directly chooses poses. A physical whole-body controller solves against body dynamics and contact forces, then sends bounded motor targets or torques into the physics step. That is the version needed for actual weight, pushes, and a one-leg hop. This family of coordinated constrained controllers is established robotics work; one example formulates prioritized humanoid control with contact constraints as a quadratic program [here](https://arxiv.org/abs/1807.01222). That citation supports the method family, not a claim that this project has implemented or benchmarked it.

For a first practical viewer, I would preserve authored clips as the style and timing reference, fit the current rig once, derive per-frame target tasks, and solve the pose as a whole. The foot state must distinguish desired contact from observed contact, so takeoff releases the anchor and landing creates a new one. The solver should report both residual errors and which constraint won, and the boss should judge whether the result has character. Only after that kinematic version is coherent should the viewer add dynamic bodies and motor forces. If the goal includes physical weight, do not present the kinematic pass as a physics result. No runtime learning is necessary for this plan. A small fixed-size solver over the mapped humanoid joints may be inexpensive enough to run locally, but actual cost needs profiling on this project and target hardware; I would not promise a frame budget before measuring it.

The boss's idea, as I understand it, is for an LLM to supply the information an animation would normally contain while a local machine turns that information into living movement. They want intent, stretch through the body, personality, and a sense of mass being carried through planted feet. They repeatedly asked to see the model actually moving in Possession rather than watch us code. They asked us to use existing animations and other models as a reference, compare joint rotations and proportions, and carry the correction across motions. They also correctly objected to treating the current balance display as a source of truth. The first generated jab/cross/hook demonstration was too basic for them. Please preserve that feedback: the feature is an experimental control surface, not an accepted fight-animation solution.

The existing `gb.studio` command selects a model, clip, time, rules, and tab; tab 1 is Possession. `gb.possess` can inspect bones, set offsets, aim segments, set grips and look, seek a frame, step, play, save corrections, and now submit a bounded motion program. An LLM sends a small description, the Rust application evaluates it locally for many frames, and the LLM can read back numbers before making another change. The LLM is not writing processor instructions or calling a language model for every joint on every frame. The application continues animating between messages. That separation is already valuable for latency and for giving the boss a live object to judge.

The strongest concept in the current implementation is reference transfer through measured anatomy. `reference_pose.rs` loads `packs/_sources/rpg_hero/fighter.glb`. It builds a shared source animation graph and spawns a hidden source scene per participating actor. Source and target sample the same named clip at the same normalized phase. For Studio, that phase is target time divided by target duration. For fighters, it comes from `FighterRig::sample_info`. The pass currently uses one hardcoded source, exact matching bone names, and a small explicit child-chain mapping. It is not a general search across our animation library, and it does not automatically learn from whichever model the boss happens to prefer. When a source clip is missing, the target retains its normal animation and subsequent constraints. Generated motion is excluded from the Studio reference pass.

The correction is more meaningful than copying local Euler numbers. Local axes and bone rolls differ between rigs. The code builds each rig's bind-space body frame from the left/right thighs and the pelvis-to-head direction. Let `A = target_frame * inverse(source_frame)`. For a mapped bone, it computes a world-space source delta `D = source_pose_rotation * inverse(source_bind_rotation)`. When a child direction exists, it also computes `R`, a rotation aligning the target bind segment direction to the aligned source bind segment direction. The implemented target orientation is `normalize(A * D * inverse(A) * R * target_bind_rotation)`. It visits parents before children and converts the desired world orientation back into local parent space. This describes the actual code, not a claim that the formula is perfect for every skeleton. Wrists use a finger anchor for their reference segment direction, including the unusual left-hand name `B_L_Forearm.001`.

The length ratio in the readout is `target_bind_segment_length / source_bind_segment_length`. It is reported separately from rotation. We do not multiply Euler angles by that ratio, and we do not lengthen bones to make a target reach the source's hand position. `procedural::bone_lengths` restores non-root, non-pelvis joint translations to the captured bind offsets before support and the final constraint passes. Two-bone IK preserves the resulting target lengths. A shorter arm needs a different reachable hand target or body placement; scaling its elbow angle by an arm-length ratio does not solve that geometry. The boss's request for visible stretch should be understood as extension, anticipation, recoil, and coordinated body motion unless they explicitly want stylized deforming bones. Our current fixed-length rule intentionally restricts literal skeletal elongation.

`RigProfile` loads sidecar data beside the selected model: `<model>.rig.json` and, when present, `<model>.body.json`. It carries joint bend ranges, maximum knee flexion, head-look bounds, mass, fitted torso sections, and limb radii. Missing or rejected data leaves defaults. Accepted mass is 10 to 300 kg; knee flexion is bounded to 45 to 150 degrees; torso radii and limb radii are also checked. These are model measurements and configured rules, not medical anatomy or a proof that every imported clip is physically possible. Joint limits operate on segment geometry to avoid bone-roll-dependent Euler clamps. The profile mass affects the current Possession estimates; it does not automatically rebuild physical rigid-body masses and inertia. That distinction matters for the future controller.

The clipping corrector in `body_clearance.rs` uses the fitted torso sections as moving elliptical volumes. It samples the elbow/forearm/wrist region, inflates the torso by the measured forearm radius plus 8 mm, and uses up to three arm-IK corrections to move the sampled arm out while preserving wrist orientation. The snapshot reports `measured`, `torso_sections`, and `forearm_penetration_m`. This is a practical geometry approximation. A zero reading means no penetration was detected at those sample points against those volumes. It does not establish zero mesh clipping, clothing clearance, upper-arm clearance, finger self-collision, continuous collision between frames, or collision with another character. There is no physical contact force in this pass.

Foot support was made less dependent on the misleading balance estimate. Studio clip playback now reads verified contact curves from `<model>.motion.json`. The shared `FootLock` state has Swing, Plant, Planted, and Release phases. A contact value above 0.65 can begin a plant and capture a world anchor. Contact below 0.35, or raw foot displacement beyond 0.22 m from that anchor, begins release. Critically damped springs move the blend weight toward one or zero, using frequencies 65 and 40 in the implementation. A plant becomes Planted above weight 0.98; release finishes below 0.005. The pelvis can lower by at most 0.1 m to keep a strongly planted foot reachable, and two-bone IK rotates the leg toward the anchor. Those choices make a recognizable foot-contact contract instead of asserting balance from a colored COM point.

The phrase contact curve needs care. It describes contact inferred or baked from a reference clip; it is an intended stance schedule, not a force measured by a physics engine. In-place Studio support uses a flat stage and sole-height data. Gameplay retains its existing sim-driven support layer and its own allowed-action logic. A contact weight is an IK blend weight, not the fraction of body weight carried by that foot. Likewise, a low anchor error is a geometric achievement, not evidence that the leg generated enough ground reaction to hold the body. I relabeled the COM display as diagnostic and removed the balanced/falling verdict. The approximate support hull and dynamic margin remain useful questions to ask of a pose, provided we do not convert them into ground truth or train an agent to optimize a misleading number.

The generated-motion path in `generated_motion.rs` is deliberately small. A program contains 2 to 240 keys, starts at zero, spans at most 30 seconds, and has increasing times at least 1/240 second apart. Every key names the same known bones. Motor-owned roots are rejected. Bone offsets use XYZ Euler degrees at the JSON boundary and become quaternions immediately. Pelvis offsets are in metres and limited to a vector length of 0.35 m. Optional `grip` contains left/right values in 0..1, and optional `hands_m` contains left/right targets in stage-relative metres. Its `plants` list selects left and/or right for the whole program. That list is not a time-varying contact schedule, so it cannot yet express stance, takeoff, flight, and landing within one physical hop.

The parser rejects rotations above the configured peak segment speed of 720 degrees/s, pelvis motion above 2 m/s or 20 m/s2, and hand-target motion above 10 m/s or 120 m/s2. These checks use the interpolation's peak factors. They are bounds on input trajectories, not on the final IK-corrected motion, and there is no equivalent general joint-acceleration check. Loop endpoints must match poses, hand targets, and grips. The interpolation uses `w = u*u*(3-2*u)`, quaternion slerp for rotations, and lerp for positions. The analytic pelvis velocity is `delta*6*u*(1-u)/dt`, and acceleration is `delta*(6-12*u)/(dt*dt)`. Parsing succeeds before the new motion replaces the old one, so a rejected motion leaves the current program intact.

Each generated frame restores bind transforms, writes the named bind-relative rotations, applies the pelvis offset in the correct parent space, and solves the specified hands. Generated foot anchors are reconstructed from bind positions, which makes them independent of the order in which frames are requested. Automatic look, grip, breathing, and lean run before manual Possession overrides; anatomical rules still run afterward. Studio life-layer sampling was made timeline-based so returning to a generated frame does not depend on how many render frames were visited first. This repeatability is useful for authoring and numerical comparisons. It does not mean all existing clip support is seek-independent: `StageSupport` has contact history, reset rules, and a synthetic 1/30-second step on reset. Dynamic physics would also have state and require reset plus replay or stored checkpoints to reproduce a frame.

The frame ordering is part of the feature, not incidental plumbing. Source reference application is scheduled after Bevy's `AnimationSystems` and before our inertialization. In `main.rs`, the ordered PostUpdate chain then performs inertialization, root locking, generated pose application, bind-length restoration, animation procedural layers, gameplay support, guard IK, fighter life layers, Studio corrections, Possession overrides, Studio contact support, generated foot plants, joint limits, torso clearance, another joint-limit pass, the knee pass, Studio/Possession measurements, ragdoll preparation, and the physics clock. That chain precedes Avian's first physics system. Physical ragdoll pose application runs after Avian's last physics system and before transform propagation. A later pass can alter an earlier pass's result. The repeated joint pass is there because clearance IK can violate a range; it does not prove all constraints converge simultaneously.

At the Rust machine level, the external message is text which `serde_json` parses into values; checked numbers become `f32`, `Vec3`, and `Quat`. `Motion`, `RestPose`, rig components, and Bevy resources hold that data in process memory. The CPU executes compiled Rust routines which sample time, multiply transforms and quaternions, solve geometric reach, and write ECS `Transform` components. `world_transform` walks the current `ChildOf` hierarchy and composes current local transforms rather than reading last frame's propagated globals. That prevents stale-parent errors during a sequence of IK writes. `ik::rotate_world` uses `inverse(parent_world_rotation) * desired_world_rotation` to store a local quaternion. After the scheduled pose/physics work and transform propagation, rendering uses the skeleton transforms and inverse bind matrices to skin the mesh on the GPU. The language model supplies data to this computation; it does not directly control assembly, the CPU scheduler, or GPU instructions.

The current code favors ease of inspection over bulk simulation speed. Several passes are exclusive `&mut World` systems, repeatedly resolve names, build maps/vectors, clone rest data, walk hierarchy depth, and allocate JSON comparisons. That is acceptable as a prototype but should be profiled before pretending it scales to thousands of actors or training environments. A future hot path could precompute bone indices, parent order, bind transforms, anatomical alignments, segment lengths, and collision descriptors when a rig becomes ready. Then sampling and inference could operate on contiguous typed arrays, while JSON stays at the authoring/inspection boundary. Bevy's ECS scheduler provides a place to order data dependencies; the explicit chain limits parallelism for the coupled pose writes. The current workspace uses Rust edition 2024, pins Bevy to 0.19.1 and Avian3D to 0.7.0, and uses development optimization level 1 for our code and 3 for dependencies. None of that implies learned control already exists.

For genuine live physics, our existing ragdoll is a starting reference, not a standing controller. `ragdoll.rs` creates 11 dynamic capsules and 10 limited joints for fighter knockdowns, inherits incoming momentum, and later blends back into authored get-up. Its hardcoded segment masses total 77 kg. It has no separate articulated foot bodies, and its collision layers intentionally omit self-collision. It is built around `FighterRig` and sim knockdown/death state, not arbitrary Studio actors. The known ragdoll hinge-axis error predates this experiment and remains open. A physically standing or hopping character needs suitable foot contact geometry, ankle control, coherent joint frames, mass/inertia, friction, torque limits, and a controller. Merely enabling the passive ragdoll will usually make it fall.

I would use the corrected reference pose as a target for bounded joint motors, with a residual controller only where needed. Conceptually, a joint controller can apply `tau = clamp(Kp*rotation_error + Kd*(desired_angular_velocity-actual_angular_velocity), torque_limit)`. Rotation error must be expressed in the joint's permitted axes; the actual implementation must use the pinned physics API and timestep, not this equation as a drop-in. Equal and opposite joint torques and actual ground contacts determine motion. A free physical root must not be teleported back to the animation every step. Some root stabilization can be useful in an assisted preview, but if it supplies arbitrary force we need to label that assistance instead of calling it self-balancing. The existing deterministic combat/movement crate remains a separate concern; a Studio physics experiment can establish physical presentation without silently changing gameplay authority.

The one-leg-hop example is useful because it exposes exactly what the boss means by weight. The character must transfer support to one foot, keep the other foot unloaded, compress the stance leg, generate a takeoff impulse through the floor, release all planted-foot constraints during flight, and absorb landing through ankle, knee, hip, and trunk coordination. At roughly Earth gravity, a 0.10 m ballistic hop needs about 1.40 m/s vertical COM speed at takeoff (`sqrt(2*g*h)`), before considering finite body geometry and rotation. For an illustrative 75 kg body accelerated from rest over 0.15 seconds, that corresponds to about 105 N*s net upward impulse, with a simple constant-force estimate of about 1,440 N average ground reaction during push-off, including gravity. These are explanatory estimates, not motor settings or measured ability. During flight the intended foot plant must release; otherwise an IK anchor would tether the character to the floor and erase the very motion we want to see.

The viewer's clock also needs explicit treatment before that experiment. Currently `props::physics_clock` pauses `Time<Physics>` and advances it using `Sim::frame_step_s`, while Studio motion can keep playing independently of the paused combat sim. Thus a moving Studio pose does not establish that physics is stepping with it. A future isolated viewer simulation needs its own coherent fixed-step clock, reset/step controls, and recorded state. Playback speed, phase advance, controller updates, physics substeps, and observation timestamps have to agree. The visual timeline should interpolate between physical states rather than alter the physical state merely because the render rate changed. This is a concrete prerequisite, not an implemented feature.

For the no-LLM runtime goal, the game can use a compact deterministic algorithm with explicit inputs and outputs. Its input is the current physical state, fitted rig profile, selected clip or movement skill, phase, and task intent already present in the game. Its output is a bounded whole-body pose or motor command. A hand-authored state machine or action selection layer can choose idle, step, strike, brace, hop, and recover; the same local body controller coordinates the selected skill with the current contacts. It need not infer intent from text. If later evidence shows a small learned policy improves adaptation enough to justify its cost, it could replace part of the deterministic controller, but the game should still run without any model file, network call, or training service. Stable per-rig joint conventions and profiles remain necessary either way.

The immediate efficiency gain does not need training: solve known geometry directly instead of asking a language model to emit many joint values or adding a large learned model to reproduce IK and limits. Fit body dimensions and rest frames once when a model loads; cache bone indices and lengths; evaluate contact and motion targets from the selected clip; run a bounded small solve each fixed physics step. The reference clips supply style, and constraints supply consistent reach and contact. This makes the runtime cheaper and more predictable. It does not automatically produce a new motion style or recover from a push unless the controller models that state and behavior. Training remains an optional research route if the deterministic controller proves too rigid.

Learned motion systems such as [DeepMimic](https://xbpeng.github.io/projects/DeepMimic/index.html), [AMP](https://xbpeng.github.io/projects/AMP/index.html), and [DiffMimic](https://arxiv.org/abs/2304.03274) show that training is one available research direction, with their own data, simulator, and compute needs. They are not the proposed first implementation here. The boss asked for an algorithm that runs cheaply and fixes movement together, so measure the deterministic whole-body method first. These papers are context for comparison if that baseline later reaches a limit, not justification to make the running game depend on a neural model.

If learning eventually warrants a separate training environment, [MimicKit](https://github.com/xbpeng/MimicKit) is an author-maintained example framework with several imitation methods and simulator backends. It is useful to study interfaces and costs before choosing a stack. A controller trained in a different engine will not automatically behave identically in Avian. Mass, inertia, joint axes, gains, friction, collision geometry, integration, solver behavior, and observation conventions can all change the result. Matching that contract and validating transfer is part of the work. We should not migrate the game engine merely to get a training demo working.

The data we would need is richer than the current live JSON snapshots. Each sample should identify source asset and clip, rig/profile version, phase, timestep, contact intent, current physical state, reference target, every important correction stage, chosen motor action, actual next state, and any fall/slip/penetration or boss acceptance. Store quaternions or a consistent continuous rotation encoding rather than rounded local Euler displays. The current snapshot rounds positions to millimetres, derives velocities from consecutive timeline samples, and approximates angular momentum and kinetic energy from weighted joint points; it lacks full rigid-body rotational inertia and measured contact impulses. Those fields are diagnostics, not a complete mechanical energy/momentum record. Record full-precision state for learning and evaluate on held-out clips and rigs, not adjacent frames randomly split from the same motion. Otherwise an impressive prediction score may just be memorizing a timeline.

I see a sensible progression from one good reference clip on one rig, to a unified kinematic solve, to a physically controlled standing/single-support task, and then a one-leg hop with deliberate takeoff, flight release, and landing. Keep the LLM out of that runtime path. Let game state and an authored action layer select the task; let the local algorithm make its per-step decisions from actual state. If it ever becomes useful to learn a policy offline, bake the result into a local asset and retain a deterministic fallback. But do not spend time training before a measurable gap in the algorithm justifies it. This is a proposed direction for Claude to assess with the boss, not authorization to start implementing this new feature now.

The application-level innovation I think is useful is the combination of live intent, anatomical transfer, explicit constraints, and an inspectable correction trail inside the game. The boss can judge motion as it happens, while we can see which stage changed which joint and why. Bevy makes that practical because asset sampling, ECS state, remote commands, CPU control math, physical simulation, and rendering can coexist with explicit ordering. None of the individual techniques is new. The potential value here is making them an authoring and feedback instrument that can also supply disciplined examples for learning. A good long-term outcome would be less per-clip corrective labor while preserving chosen movement style, not simply replacing every useful rule with a black box.

Having read this back against the implementation, the first extra insight is that our reference pass is stronger than the word corrector suggests. `correct` writes the desired orientation directly for each mapped bone. `FighterRig::sample_info` reports the current node, and gameplay locomotion sets that node to the dominant member of its blend. The reference then samples that single source clip and writes mapped rotations over the blended target pose. Consequently, for matching source clips it can erase part of the authored blend or transition before inertialization and later procedural layers. This follows directly from the code; I have not measured a new gameplay regression in this documentation turn. Please review that interaction before promoting the pass across the whole game. A future corrector could transfer a matched source blend, apply a calibrated mapping correction to the blended pose, or be gated to explicit inspection mode. Copying one dominant reference pose is not equivalent to correcting all clips in a blend.

There is another narrower point in the mapping. The current pass transfers rotations, not source pelvis translations or source trajectory. It also uses one child direction to resolve a rest alignment, which cannot by itself resolve every twist convention about that direction. The separate source and target bind quaternions supply more orientation information, but this still deserves inspection on rigs with different rolls, handedness, scale, or extra spine joints. If the boss sees a correct-looking limb angle but loses a hip-driven sway or reach, the rotational comparison may be functioning while the overall body motion remains wrong. The next useful representation might preserve foot/hand paths and pelvis intent in normalized body space as well as joint rotations. That is a stronger interpretation of their request to compare ratios across models than rescaling a set of angle numbers.

The tight foot-error sample needs an explicit correction to how we talk about our evidence. `support::stage` stores `leg.solved` immediately after its IK pass. `stage_snapshot` calculates anchor error from that cached position. The final joint, clearance, joint, and knee passes occur afterward. A knee correction can move the foot, yet `clip_support.anchor_error_m` still reports the earlier solved position. Gameplay support has a similar cached solved field. Thus the approximately 0.002 mm figure proves the support pass hit its target at that point in the pipeline; it does not prove the final rendered foot stayed that close. Final-pose measurement against the same anchor would resolve this. For dynamic actors, that final measurement must also account for the physical override after physics, since our current Studio/Possession measurements precede it. I am documenting the mismatch rather than editing it under a reasoning-only request.

Missing data should also be visible in a future observer. `stage_snapshot` returns its stored rig data without a dedicated assertion that the currently selected clip has a valid contact curve. On a clip with no such curve, a previously built state can leave misleading old fields. Generated snapshots report bind-anchor distances even for a foot which was not requested to plant, and the clip snapshot reports distances during release and swing. Those distances are not failures by themselves. Training labels and inspection UI should distinguish intended contact, active geometric lock, measured physical contact, and final foot error under that contact. This would prevent the same mistake we already caught in the COM display from recurring under a different metric name.

Rereading the smoothstep sampler also suggests a concrete reason the initial generated fight felt basic. Its velocity is zero at every key, even when a key is supposed to be an intermediate point in a flowing strike. Its acceleration can jump between adjacent segments and across a closed loop. Matching loop endpoints closes the pose and gives zero endpoint speed, but does not match acceleration. That tends to produce repeated easing and stopping instead of a continuous hip-to-shoulder-to-hand transfer. Better references, meaningful velocity tangents, consistent contact events, and a coordinated timing model may improve personality before any neural training. A network trained only on those basic smoothstep demonstrations could faithfully reproduce the exact stiffness the boss dislikes. Visual judgment remains part of selecting the teacher data.

The weight question now seems even clearer to me: the important signal is how the body responds when the expected support is missing or disturbed. A kinematic pose can hold a COM outside its feet indefinitely because it has no obligation to fall. In a physical hop, the support foot must supply admissible ground reaction: a nonnegative normal force, tangential force limited by friction, and enough impulse without exceeding the joints' available torque. A contact curve cannot guarantee those conditions. Physical contact feedback should decide whether the requested stance is actually available, while reference phase supplies intent. The controller may need to delay push-off, alter the landing target, or take a recovery step instead of forcing the timeline to finish. That small distinction between intent and observed support is probably the most important concept for the neural version.

I would also avoid using literal bone elongation to compensate for that physical shortfall. A visibly stretched pose can come from shoulder elevation, trunk rotation, extension through hip/knee/ankle, and opposing recoil while lengths stay fixed. If the boss later wants squash-and-stretch as an art effect, it can be a deliberate visual deformation layered over a well-defined physical skeleton. It should not silently change the physics segment geometry or leak into the training labels as impossible reach. This lets personality and physical weight work together without making every character proportion a new exception.

There is a useful training shortcut hiding in the distinction between pose repair and physical recovery. Much of pose repair may be cheap enough to keep as a deterministic algorithm forever: precomputed anatomical mapping, fixed lengths, a small IK solve, and model-specific clearance. Learning those again would spend data reproducing something we already know. A policy can instead concentrate on the residual needed to make the moving body follow the desired motion under actual contacts. If we eventually distill some expensive repair into a network, record both the proposed and corrected actions and keep the geometric checks as a fallback. Otherwise the teacher's repairs hide bad policy choices from the training signal. First measure whether a network is even faster or more useful than the small analytic pass it would replace.

My final added insight is that a well-made live viewer can be the test bench for this deterministic algorithm, rather than a place to watch an AI improvise every pose. It should let the boss select a skill, see the character move under the same local rules the game will use, and inspect final foot contact, reach, collision clearance, and tracking error. First establish one stable standing pose, then single support, then a measured hop with a real landing. If it cannot do those without hidden pose teleporting, the physical controller is not ready. The existing reference and measurement work still helps by giving the solver a style target and usable rig geometry; the change in direction is that one coordinated Rust algorithm owns the live correction. The language model can remain an optional development tool outside the game, while the shipped movement runs from ordinary data and code.

The boss has now made the animation-normalization idea more precise, and this should be treated as the current direction. The target of uniformity is each model's own anatomy and coordinate system. A punch, a run, and a recovery should remain different movements. What should become consistent is how every clip expresses that movement on the chosen character: which bones correspond, what their rotations mean in that rig's anatomical frame, what the limb proportions permit, how the body carries momentum, and when contacts happen. Think of it as decompiling clips into a shared movement language, correcting them for one model, then rebuilding usable clips and transitions. The user-made short animation is especially valuable as an exemplar. It can be a weighted source of truth for the movement qualities the boss likes, while model measurements and physical constraints determine what the character can actually perform.

K-means can help separate clips by movement family before building that shared representation. Cluster whole clips or comparable motion windows from carefully selected features: canonical joint rotations and angular velocities, pelvis and hand/foot trajectories relative to body scale, duration/phase, contact patterns, and perhaps attack or locomotion metadata when the game already provides it. Do not cluster unnormalized raw Euler values or flatten every sample without preserving phase; those distances confuse different bone rolls, proportions, and timing. Map each rig into canonical anatomical coordinates first, express translation relative to a stable body frame and stature, and use a rotation representation with sensible angular distance. Then group similar clips such as locomotion directions, punches, kicks, reactions, idles, and recoveries. A jab should not be averaged with a run simply because a few joint numbers happen to be close.

K-means is a useful first partitioning tool, not the motion fixer itself. It minimizes distance to cluster centres; it does not understand action semantics, guarantee smooth transitions, label takeoff, or enforce foot contact. A clip that contains several phases may need windows or phase-aligned features; a cluster centre is a summary, not necessarily a real animation that should be played. Start with transparent features, a fixed or validated cluster count, inspect which clips land together in the viewer, and allow ambiguous clips to remain unassigned or be reviewed. Keep the original clips and record every correction. Cluster only to determine which examples should inform one another and which transition candidates are plausible. Never average joint poses from different clusters into one generic action.

Within each movement family, use a canonical per-model skeleton map, bind frame, measured segment lengths, joint rules, fitted body volumes, and contact curves to normalize the clip. Compare the user's exemplar to members of its relevant family and weight it strongly for the qualities it demonstrates. Other compatible clips contribute coverage and variation. Hard constraints such as reach, foot contact feasibility, joint limits, and torso clearance must outrank all reference weights. Style similarity should be a soft target with a reported residual, not a command that forces an impossible pose. Preserve action identity, timing, and useful source details; synthesize corrected trajectories only where the shared rules expose an inconsistency. Then connect family-specific clips through transitions whose end/start poses, velocities, and contact states agree. This is how a system can make a cycle feel like one character without making every action look the same.

This is also where the current implementation is only a beginning. `reference_pose.rs` currently compares one hardcoded source rig to a target for matching clip names and directly applies mapped rotations. It has no clip clustering, no exemplar weights, no canonical motion database, no synthesized corrected-clip export, and no transition graph built from endpoint compatibility. Its direct gameplay correction may overwrite a dominant clip over a blended pose, so review that before enabling broad normalization in gameplay. The fixed-length IK, profile loading, clearance approximation, contact anchoring, and live numeric inspection are useful building blocks. The final-pose readout issue noted above should be repaired before its measurements become algorithm inputs or acceptance scores.

For the physical part, keep the same family-specific reference as desired movement, but let observed physics decide whether each contact actually exists. A clip says when a foot intends to plant; the solver confirms the foot is in contact, checks forces and reach, and may adjust timing or trajectory. During a hop, it must release the stance anchor at takeoff, let the free leg move, and capture a real landing. The physically based stage must preserve mass, inertia, joint torque bounds, and friction; cosmetic pose correction cannot stand in for this. First prove the normalization and flow kinematically on the target model, then prove a single physical action from push-off through recovery.
